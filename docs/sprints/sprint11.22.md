# Sprint 11.22 — Public Report Contract Hardening

## Goal

Strengthen the AI Test Lab public report boundary by proving that a report generated by the framework can be:

1. Generated from a real runtime result.
2. Mapped into the public report contract.
3. Validated against the published JSON Schema.
4. Written to disk.
5. Read back through the public report reader.
6. Consumed through the public consumer facade.
7. Converted into summary, decision, and assessment outputs.

The sprint also verifies that internal and proprietary runtime information does **not** leak into the public report.

---

## Why This Sprint Matters

Previous Sprint 11 work established the major pieces of the public reporting architecture:

* Public report DTOs.
* Explicit runtime-to-public mapping.
* JSON Schema validation.
* Schema-version validation.
* Public report reading.
* Report inspection.
* Report summarization.
* Report decision logic.
* Report assessment.
* Public report consumer facade.
* Public/private boundary protections.

Those components were already individually tested.

Sprint 11.22 adds an important missing verification:

> **Can a report produced by the real AI Test Lab reporter travel through the entire public contract and be successfully consumed without relying on internal runtime implementation details?**

This sprint answers that question with an end-to-end contract test.

## IP Protection Boundary

AI Test Lab maintains a deliberate boundary between:

```text
Internal Runtime
        |
        | explicit allow-list mapping
        v
Public Contract
```

Internal runtime objects are **not serialized directly**.

Instead, data crosses the boundary through explicit public DTOs and mapper functions.

Sprint 11.22 verifies this behavior end-to-end.

### Private Runtime Data Used by the Test

The test deliberately injects internal values such as:

```text
internal_scoring_strategy
private_evidence_id
C:\private\governance\engine.py
```

These values simulate implementation details that must remain private.

---

## Runtime Option Filtering

The runtime evaluation contains both public and private options.

Example:

```python
runtime_options={
    "include_reason": True,
    "internal_scoring_strategy": "proprietary-v5",
    "private_evidence_id": "EV-1122",
}
```

Only the explicitly approved public option is allowed through the reporting boundary.

Expected public representation:

```json
{
  "include_reason": true
}
```

The following private fields must not appear in the serialized report:

```text
internal_scoring_strategy
private_evidence_id
```

The end-to-end test verifies their absence.

---

## Engine Error Sanitization

Internal engine errors may contain implementation information such as:

```text
C:\private\governance\engine.py
```

Such information must not become part of the public contract.

The public report instead exposes the normalized message:

```text
Evaluation engine failed.
```

The test verifies that neither the private path nor the internal filename survives serialization.

---

## Schema Validation

The generated report is validated using:

```python
validate_report_payload(payload)
```

The report declares:

```json
{
  "schema_version": "1.0"
}
```

The validator selects the appropriate published contract:

```text
schemas/report-v1.0.schema.json
```

Therefore, the integration test verifies the actual published JSON contract rather than only validating Python objects.

---

## Consumer Verification

After generation and validation, the report is consumed using:

```python
consume_report(report_path)
```

The consumer successfully produces:

```text
ReportConsumption
    |
    +-- report
    +-- summary
    +-- decision
    +-- assessment
```

The test verifies important consistency rules, including:

```text
summary.total == 1
summary.passed == 1
summary.failed == 0
summary.errors == 0
```

It also verifies that the decision and assessment agree on report status.

## Architectural Principle

The public report is treated as a stable external contract rather than a serialization of AI Test Lab's internal Python models.

The intended architecture remains:

```text
Internal Models
      |
      v
Explicit Mapper
      |
      v
Public DTO
      |
      v
Published JSON Schema
      |
      v
Public Artifact
      |
      v
Public Consumer
```

This separation allows internal AI Test Lab capabilities to evolve independently.

For example, internal:

* evaluation logic,
* scoring strategies,
* governance mechanisms,
* evidence intelligence,
* orchestration,
* compliance logic,
* engine implementation details,

do not automatically become part of the public API or report format.

Only deliberately approved fields cross the public boundary.
